# smallcode 開発設定

この文書は、これまでの会話で決定した開発・実行環境をまとめたものです。
記録日：2026-10-25。ブランチの状態は作成時にローカルで確認しています。

## リモートとブランチの役割

| 名前 | 接続先・役割 |
| --- | --- |
| `origin` | 自分のfork：`git@github.com:Hashi1zume/smallcode.git` |
| `upstream` | fork元：`https://github.com/Doorman11991/smallcode.git` |
| `master` | fork元の `upstream/master` に追従する。独自変更は原則入れない |
| `dev_master` | 独自変更の統合先であり、ホストで実行するブランチ。追跡先は `origin/dev_master` |
| `feature/TalkOnly_NoCoding` | `dev_master` から作成した機能開発用ブランチ |

fork元のブランチ名に合わせて `master` を使用する。途中で作成した `main` と
`dev_main` は、ローカル・forkの双方から削除済み。
`upstream` の登録だけでは更新は自動反映されない。

## worktree の構成

```text
/Users/hashizume/project/
├── smallcode/          # dev_master：通常版の実行用
└── smallcode-feature/  # feature/TalkOnly_NoCoding：開発用
```

`git worktree` により、同じGitリポジトリのブランチを別ディレクトリで同時に扱う。
履歴とブランチ情報は共有するが、作業ファイル・未コミット変更・`node_modules` は独立する。
同じブランチを複数のworktreeで同時にチェックアウトすることは通常できない。

## 通常版の起動

```bash
cd /path/to/作業対象
smallcode
```

`npm link` でグローバル登録済み。現在のリンクは次の関係になっている。

```text
/opt/homebrew/bin/smallcode
  → /opt/homebrew/lib/node_modules/smallcode/bin/smallcode.js
  → /Users/hashizume/project/smallcode/bin/smallcode.js
```

`smallcode` はどのディレクトリでも、この実行元のコードを使う。
起動したディレクトリが作業対象になる。
`smallcode-feature/` に移動して `smallcode` と入力しても、通常版が起動する。

元の `smallcode/` は `dev_master` に固定して運用する。
ここでブランチを切り替えると、次回起動時の通常版のコードも切り替わる。
ディレクトリの移動・削除はグローバルリンクに影響する。

## 開発版の起動

```bash
cd /Users/hashizume/project/smallcode-feature
npm start
```

`npm start` は、そのworktreeの `node bin/smallcode.js` を実行する。
開発用worktreeでは `npm link` を実行しない。実行すると通常版のリンク先が変わり得る。

別々のターミナルで通常版と開発版を同時に起動できる。
ただし、グローバル設定やモデルサーバーは共有される場合がある。
起動中のプロセスにコード変更は自動反映されないため、変更後は終了・再起動する。

全画面UIに問題がある場合：

```bash
# 通常版
smallcode --classic

# 開発版（smallcode-feature/ 内）
npm start -- --classic
```

終了は入力欄で `/quit`。
起動時の `Code graph:` は入力欄ではなく初期化状況の表示で、Enterは不要。
処理後に `✓ indexed` または `disabled` が表示される。
そこで止まる場合は入力待ちとは限らず、初期化の状態を調べる。

## 依存関係とモデル接続

- 必要環境はNode.js 18以上、npm、Git。
- 両worktreeに実行用依存関係を `npm install --omit=dev --package-lock=false` で導入済み。
- 開発用の依存関係も必要なら、そのworktree内で `npm install` を実行する。
- ブランチの切り替えやマージで依存関係が変わった場合も、インストールを実行する。
- モデルを利用するには、モデルサーバーと適切な接続設定が必要。

`.env` の読み込み候補は、起動ディレクトリの `.env`、`.smallcode/.env`、
`~/.config/smallcode/.env`、`~/.smallcode/.env` の順で、最初に見つかったファイルを使う。
`smallcode.toml` などの設定もあるため、実行元リポジトリの設定が
別ディレクトリからの起動でも自動的に使われるとは限らない。
個人用設定やAPIキーを不用意にコミットしない。

## 機能開発の進め方

既存の機能ブランチで開発する場合：

```bash
cd /Users/hashizume/project/smallcode-feature
git status
# 編集・テスト
git add 対象ファイル
git commit -m "変更内容"
```

この機能ブランチに最新の `dev_master` を取り込む場合は、未コミット変更を整理してから：

```bash
git merge dev_master
```

別の機能を `dev_master` から始める場合：

```bash
git switch -c feature/新しい機能名 dev_master
```

現在の機能ブランチから派生させるなら、最後の `dev_master` を省略する。
切り替え前には開発版を終了し、変更をコミットまたは退避する。
forkへ機能ブランチを登録する場合：

```bash
git push -u origin feature/TalkOnly_NoCoding
```

## dev_master への統合

1. 機能ブランチで変更をコミットし、関連するテストを実行する。
2. 通常版を終了し、実行用ディレクトリで状態を確認する。

   ```bash
   cd /Users/hashizume/project/smallcode
   git status
   git branch --show-current
   ```

3. `dev_master` であることを確認し、未コミット変更を整理してから統合する。

   ```bash
   git merge feature/TalkOnly_NoCoding
   ```

4. 競合があれば解消し、必要な依存関係の更新とテスト・起動確認を行う。
5. 確認済みの内容をforkに反映する。

   ```bash
   git push origin dev_master
   ```

6. `smallcode` を再起動して統合後のコードを使用する。

一時退避には `git stash push -u -m "退避内容"` が使える。
復元時の `git stash pop` でも競合する可能性があるため、結果を確認する。

## fork元の更新を取り込む

作業ツリーを整理してから、実行用ディレクトリを `dev_master` のまま維持しつつ、
別worktreeで使用されていないローカル `master` を更新する：

```bash
cd /Users/hashizume/project/smallcode
git fetch upstream
git fetch . refs/remotes/upstream/master:refs/heads/master
git push origin master
git merge master
```

ローカル `master` の更新は、履歴が分岐している場合には拒否される。
拒否時は強制更新せず、差分を調査する。
`dev_master` へのマージ後は、競合解消・テスト・起動確認を行ってから
`git push origin dev_master` する。
